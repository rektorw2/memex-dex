# Независимое ревью production follow-up

Дата: 2026-09-09. Проверена текущая незакоммиченная рабочая копия поверх 619e631. Реализация, production и исходный отчёт автора не изменялись.

## Результат

Перед публикацией рекомендовано исправить два воспроизведённых дефекта восстановления. Общие заявления автора о 4369 тестах / 91 E2E не опровергаются: дополнительные сценарии отсутствуют в штатном наборе.

### [P2] Запрос метаданных теряется при занятом слоте

Места: `apps/api/src/workers/paper-agent.ts:438–445`, `apps/api/src/services/paper-token-metadata.ts:13–16`.

Воркер сначала сохраняет `decisionCode=WAITING_FOR_TOKEN_METADATA` условным обновлением строки с `decisionCode=null`, затем вызывает запрос. Сервис возвращает void и может немедленно отказаться из-за паузы между запросами или лимита параллелизма. Воркер не узнаёт об отказе; последующие проходы не получают claim, потому что decisionCode уже заполнен. Таким образом, попытка считается использованной даже без сетевого запроса.

Воспроизведение: другой токен занимает первый запрос; свежий сигнал проходит в ожидание метаданных во время пят секундной паузы; спустя шесть секунд у сервиса есть свободная ёмкость и у сигнала ещё есть время до дедлайна, но повторный проход настоящего worker не вызывает провайдера. Ожидалось два вызова (другой токен и проверяемый), фактически один. В тесте использованы настоящий worker и настоящий metadata service; подменены база, источник метаданных и прочие внешние зависимости из существующего worker-теста.

Последствие: при пакетном поступлении сигналов дата активно запрашивается только для части токенов, остальные зависят от случайного обновления общего кэша и получают окончательный пропуск. Существующий тест сервиса проверяет ограничение нагрузки, но не последующее обслуживание отложенного токена.

Исправление: различать ожидание слота, фактический запуск и завершённую попытку. Возвращать результат постановки/запуска и сохранять возможность ограниченного повтора до исходного дедлайна; учитывать многопроцессный запуск и рестарт. Не снимать лимиты, не создавать бесконечную очередь и не продлевать срок сигнала.

### [P2] Ошибка Market-списка оставляет сети без повторной проверки до часа

Место: `apps/api/src/workers/okx-signal-ingest.ts:399–420`.

Общий интервал обновления определяется только наличием Signal-списка. После успешного Signal-ответа и отказа Market-запроса Signal уже считается известным, а следующая попытка обоих запросов назначается через час. Собственного короткого повтора у неподтверждённого Market-списка нет. Дополнительно истёкший Signal getter возвращает `[]`, для которого проверка `!= null` также выбирает часовой интервал.

Воспроизведение с настоящими ingest/OKX-клиентом: Signal возвращает 200 с сетью 501, Market — 403; через две минуты повтор `refreshSignalSupportedChains` не делает ни одного запроса. Неподтверждённый Market остаётся null. При исправлении доступа в течение этого окна автоматическое восстановление произойдёт только по следующему часовому таймеру. Robinhood без подтверждения цен остаётся недоступным; после истечения старого подтверждения проблема затрагивает и другие проверяемые сети.

Исправление: независимые отметки успеха и расписания повторов Signal/Market. Не полученные, неудачные и истёкшие проверки должны повторяться с ограниченным backoff; часовой refresh применим к действующему успешному подтверждению. Сохранять явное отличие пустого ответа от отсутствующего/истёкшего. Добавить тесты раздельного отказа и восстановления обоих списков.
