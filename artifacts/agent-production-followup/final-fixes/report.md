## 1. Метаданные: ожидание слота больше не расходует попытку

Причина: worker записывал `WAITING_FOR_TOKEN_METADATA` как одноразовый claim до вызова сервиса. Сервис возвращал `void`, в том числе при отказе из-за интервала 5 секунд или двух занятых слотов. Следующий проход не получал claim и уже никогда не обращался к провайдеру.

Теперь `RECEIVED / WAITING_FOR_TOKEN_METADATA` означает ожидание даты, а не доказательство запущенного запроса. Каждый допустимый проход может спросить сервис о допуске. Сервис возвращает явный результат: `accepted`, `waiting_capacity`, `in_flight`, `completed`, `exhausted` или `expired`. Результат записывается в диагностический лог вместе с run/token. Источником истины о попытках служит отдельный журнал допуска в PostgreSQL.

- Одна строка `PaperMetadataGate` под транзакционной блокировкой `FOR UPDATE` координирует все стратегии и процессы. Время допуска берётся из базы после получения блокировки.
- Общие ограничения: один допуск не чаще 5 секунд, максимум две незавершённые аренды слота; дедупликация по tokenId сохраняется между процессами и рестартами.
- Незавершённая аренда истекает через 15 секунд; разрешено одно восстановление, всего максимум две попытки на токен в минутном окне. Завершённая попытка не запускается повторно в этом окне. Владелец попытки имеет уникальный идентификатор: позднее завершение старой попытки не закрывает новую.
- Локальный лимитер провайдера также должен немедленно выдать слот. Если он занят или действует backoff провайдера, внешний запрос не начинается, попытка освобождается, результат — `waiting_capacity`. Метаданные не добавляются в очередь импортёра.
- HTTP ограничен 10 секундами, концом исходного срока сигнала и сроком аренды. Перед запуском снова проверяется срок; просроченный ответ не записывается.
- Срок ожидания — минимум из `signaledAt + maxDecisionLatencyMs` и `receivedAt + 30 секунд`. Эти отметки сохранены в сигнале; доставка или рестарт их не изменяют. Нет новой очереди: журнал хранит только ограниченное окно допусков и очищается при обращениях; активная аренда сохраняется до своего конца.
- Дата по-прежнему берётся только из достоверного ответа провайдера, записывается только в пустое `Token.poolCreatedAt`. После её появления worker заново проверяет возраст, свежесть сигнала и остальные условия. Окончательные решения и закрытые позиции не переоткрываются. Управляемый `TEST_HARNESS` по-прежнему не вызывает внешнего провайдера.

Основные файлы: [worker](../../../apps/api/src/workers/paper-agent.ts), [сервис допуска](../../../apps/api/src/services/paper-token-metadata.ts), [лимитер провайдера](../../../apps/api/src/services/market-data.ts).

## 2. Signal и Market восстанавливаются независимо

Причина: одна отметка попытки и выбор часового интервала по наличию Signal-списка. Успех Signal скрывал отказ Market; отказ Signal вообще прерывал проверку Market. Истёкший Signal возвращал `[]`, который также ошибочно считался известным успешным подтверждением.

Теперь для каждого списка отдельно учитываются последняя попытка, успешный ответ, отказ и выполняющийся запрос. Проверки запускаются независимо. Действующий успешный ответ обновляется раз в час; после отказа, отсутствующего или истёкшего подтверждения повтор разрешён через минуту. Это фиксированный ограниченный backoff: повторные проходы не создают запросов внутри минуты. Отказ часового refresh также приводит к минутному повтору, даже пока предыдущее подтверждение ещё действует.

Новый статус подтверждения явно различает `missing`, `valid` и `expired`, сохраняя время успеха. Успешный пустой список — `valid`, обновляется по часовому расписанию и не разрешает сети. Совместимые getters по-прежнему возвращают `[]` для истёкшего списка: старое подтверждение не используется для допуска. На каждый список действует отдельная защита от пересечения запросов.

Файлы: [refresh worker](../../../apps/api/src/workers/okx-signal-ingest.ts), [подтверждения OKX](../../../apps/api/src/services/okx-market.ts).

## Миграция и план публикации

Добавлена только [20260909120000_add_paper_metadata_gate](../../../prisma/migrations/20260909120000_add_paper_metadata_gate/migration.sql): новая таблица `PaperMetadataGate` с ключом и ограничением единственной строки `id=1`. Существующие таблицы, решения, позиции и данные не изменяются. Миграция включена в явный каталог проверки схемы и проверена штатным `prisma migrate deploy` на изолированной PostgreSQL. Предыдущие неопубликованные миграции `AgentLiveWallet` и `WorkerHeartbeat` по-прежнему нужны.

При будущей, отдельно разрешённой публикации: резервная копия и проверка текущего состояния → штатное применение всего ожидаемого набора миграций → запуск новой версии → проверка схемы, здоровья API и тиков воркера → проверка допуска метаданных и независимого восстановления списков. Старый worker с прежним локальным лимитером следует завершить до запуска новых обработчиков: он не участвует в новом общем журнале. Несколько процессов новой версии используют общий лимит базы.

Локальная репетиция: новый образ → точный `619e631` → новый образ, на клоне обновлённой E2E-базы. На всех трёх этапах `/health` = 200, схема готова, хеш полного набора данных одинаков. `PaperMetadataGate`, `AgentLiveWallet`, `WorkerHeartbeat` и `_prisma_migrations` сохранены. Историю миграций и добавленные таблицы при откате удалять не нужно. Воркеры в репетиции выключены: это проверка схемы, старта API и сохранности данных, а не сопровождения открытых позиций старой версией. Локальный образ содержит проверенное поведение; последующие изменения исходников — только комментарии/форматирование/имя переменной и тесты.
