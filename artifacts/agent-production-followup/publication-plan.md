# План публикации и безопасного отката

Это инструкция для отдельного разрешённого окна публикации; сейчас ни один production-шаг не выполнен. Она заменяет ошибочные рекомендации предыдущих отчётов удалять `_prisma_migrations`, AgentLiveWallet или WorkerHeartbeat.

1. Проверить итоговый diff и новые файлы. Отдельно сформировать ревью/коммит; не включать автоматически все чужие артефакты рабочей копии. Зафиксировать точный образ/ревизию, текущий Render-план и резервную копию базы.
2. Перед изменениями перечитать `PaperAgentControl`, активные сессии/позиции, runtime, источник и сети. Состояние могло измениться извне. Согласовать окно и при необходимости приостановить новые PAPER-входы штатным Stop, сохраняя сопровождение открытых позиций.
3. Применить все три добавочные миграции: `20260908130000_add_agent_live_wallet`, `20260909100000_add_worker_heartbeat` и `20260909120000_add_paper_metadata_gate` — через проверенный entrypoint новой версии (или один штатный migrate deploy по DIRECT_DATABASE_URL в согласованном процессе). Не запускать два независимых механизма миграции одновременно. После запуска проверить `production schema: ready` и отсутствие незавершённых миграций.
4. Опубликовать согласованный API и статический web. Render blueprint содержит `1c-2g`; отдельно проверить, что применение blueprint сохраняет выбранный владельцем размер. Правка YAML не равна применению.
5. Проверить `/health`, `/health/agent`, отдельные worker/source состояния и текущие Signal/Market/RPC подтверждения. Для новых официальных сигналов сопоставить все включённые strategyId, решения, snapshot даты и обе задержки. Пропуск — корректное решение, но не доказательство готовности PAPER-торговли.
6. После проверки доступа OKX дождаться редкого повтора WS или выполнить отдельно разрешённый явный повтор. Требуются login, subscribe acknowledgement и настоящее событие. REST должен продолжать работать при отказе WS.
7. Подтвердить допустимый PAPER-вход, сопровождение и выход; запустить наблюдение с новым сборщиком и суммаризатором из `observe/` на ≥24 часа. CSV с пробелами/рестартами/отсутствующими метриками не считать PASS. Не менять лимиты ради получения сделки. Не включать LIVE или broadcast.

## Что проверено при откате

Изолированная PostgreSQL 17 получила все миграции через штатный E2E. Её отдельный клон сохранил обычные тестовые данные; добавлены непустые записи выбора Robinhood-кошелька и heartbeat. Настоящий Docker entrypoint новой версии, затем точного `619e631`, затем новой версии выполнил проверку схемы и запустил API. Каждый /health вернул 200; checksum полного data-only dump совпал до и после всех трёх запусков. История миграций и обе добавленные таблицы остались нетронутыми.

В `619e631` UNKNOWN_MIGRATION_PRESENT проверяет **каталог миграций образа**, а не дополнительные успешно применённые записи базы. Удаление истории не требуется.

## Как откатываться

- Остановить новые входы штатным контролем. Сохранить резервную копию и журналы. Не стирать позиции, сессии, ledger, выбор кошелька, heartbeat или историю миграций.
- **Не возвращать активный worker `619e631`, если есть открытые позиции BNB/Robinhood либо позиции, для сопровождения которых нужны новые сетевые модели расходов.** Сначала завершить их новым совместимым worker либо использовать отдельно проверенный совместимый rollback-образ. Старый API можно откатить отдельно от совместимого worker; оставлять активные позиции без сопровождения нельзя.
- Если активных позиций нет, вернуть старый образ с новыми входами на паузе. Дополнительные таблицы и строки `_prisma_migrations` оставить. Проверить schema ready и /health; `/health/agent` в старой версии отсутствует, это ожидаемый 404, а не повод удалять данные.
- Возврат на новую версию использует ту же базу и тот же штатный entrypoint. Он должен увидеть уже применённые миграции; повторных вставок/удалений истории не нужно. Перечитать текущие состояния, дать истёкшим ожидающим сигналам получить пропуск и возобновлять входы только в согласованном порядке.

Граница проверки: в контейнерном rehearsal `RUN_WORKERS_IN_API=false`, чтобы сравнить сохранность всех данных при переключении образов. Это доказательство совместимости схемы и запуска API, **не** доказательство безопасного сопровождения новых сетевых позиций старым worker. Новое сопровождение и идемпотентность проверены отдельно штатным E2E. Production-база не клонировалась и не менялась.
