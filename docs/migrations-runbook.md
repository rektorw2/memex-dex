# Переход на историю миграций

Порядок действий для боевой базы. **Ни один шаг этого документа
не выполнен.** Здесь только подготовленная последовательность.

Prisma: **6.19.3** (`node -p "require('prisma/package.json').version"`).
Синтаксис команд ниже — этой версии.

## Зачем

Схема правилась командой `prisma db push`. Она приводит базу
к виду файла и не оставляет записи о том, что именно изменила.
Пока таблиц мало и данные не жалко, этого хватает. Дальше — нет:
`db push` умеет удалить колонку, чтобы схема сошлась, и делает это
молча.

Переход устроен так, что боевые таблицы не пересоздаются.
`0_baseline` описывает базу, которая **уже есть**, и на боевой базе
не выполняется — только помечается выполненным. Всё, что появилось
после, едет отдельной миграцией.

## Что подготовлено

| Файл | Строк | Содержимое |
| --- | --- | --- |
| `prisma/migrations/0_baseline/migration.sql` | 1034 | 30 таблиц, 19 перечислений, 82 индекса, 30 внешних ключей |
| `prisma/migrations/20260821120000_add_subscriptions_and_trial/migration.sql` | 109 | 2 таблицы, 3 перечисления, 5 колонок в `User`, 8 индексов, 2 внешних ключа |
| `prisma/baseline.prisma` | — | Снимок схемы до новых моделей. Нужен для сверки. Не редактировать |

`DROP` не встречается ни в одном файле. Единственный `ALTER TABLE`
существующей таблицы — добавление пяти колонок в `User`, все
необязательные или с умолчанием, поэтому существующие строки
он не трогает.

```bash
grep -nE '^\s*DROP' prisma/migrations/*/migration.sql          # пусто
grep -nE '^\s*ALTER TABLE .* DROP' prisma/migrations/*/migration.sql  # пусто
```

## Что уже проверено локально

`npm run db:verify` поднимает настоящий Postgres (PGlite — Postgres,
собранный в WebAssembly) и прогоняет два сценария:

1. **Чистая база.** `0_baseline`, затем feature-миграция. Проверяются
   32 таблицы, три новых перечисления, все индексы и внешние ключи,
   отказ базы принять второй активный план у одного пользователя
   и отказ выдать второй пробный период.
2. **Копия существующей базы.** Только `0_baseline`, поверх него —
   строки пользователя и находки радара, и только потом
   feature-миграция. Проверяется, что строки на месте и значения
   не изменились.
3. **Путь боевой базы.** Baseline помечается выполненным, а не
   выполняется; применяется только feature-миграция; повторный прогон
   ничего не делает.

Все три сценария проходят. Это не заменяет проверку на клоне боевой базы:
локальная база создана из baseline, а боевая — из истории команд
`db push`, и расхождение между ними как раз и надо найти.

## Шаг 0. Сверка боевой базы со снимком схемы (только чтение)

```bash
echo '<прямая строка подключения без -pooler>' > ~/.memex-prod-url
chmod 600 ~/.memex-prod-url
npm run db:drift
```

Скрипт читает боевую схему и печатает SQL, который привёл бы её
к виду `prisma/baseline.prisma`. Строка подключения не попадает
ни в вывод, ни в текст ошибок — вывод пропускается через замену.

Возможны два исхода.

**Расхождений нет.** Скрипт создаёт пометку `prisma/.drift-checked`.
Переходите к шагу 1.

**Расхождение есть.** Это ожидаемо, а не исключительно: схему меняли
командой `db push` не один раз, и след таких изменений существует
только в самой базе. Каждую строку разницы надо либо перенести
в `prisma/baseline.prisma` и пересобрать baseline
(`bash scripts/migrations-prepare.sh` после удаления старой папки),
либо объяснить письменно, почему она допустима. Пометить baseline
выполненным при неразобранном расхождении нельзя: Prisma поверит
на слово и перестанет замечать разницу, а разница никуда не денется.

Сравнивать нужно: таблицы, колонки, типы, обязательность, умолчания,
внешние ключи, уникальные ограничения, индексы, значения перечислений,
а также то, чего Prisma не описывает вовсе — расширения, триггеры,
представления, частичные индексы. Последнее в проекте пока
не используется; если появится, эти объекты добавляются в baseline
вручную и документируются здесь.

## Шаг 1. Проверка на клоне боевой базы

Ветка Neon от боевой базы — это и есть клон.

```bash
# 1. Создать ветку в Neon от текущего состояния боевой базы.
# 2. Строку подключения ветки положить в переменную окружения.
export CLONE_URL='<строка подключения ветки, без -pooler>'

# 3. Пометить baseline выполненным — SQL при этом НЕ исполняется.
DATABASE_URL="$CLONE_URL" npx prisma migrate resolve --applied 0_baseline

# 4. Посмотреть, что осталось применить.
DATABASE_URL="$CLONE_URL" npx prisma migrate status

# 5. Применить feature-миграцию.
DATABASE_URL="$CLONE_URL" npx prisma migrate deploy

# 6. Убедиться, что схема и база сошлись. Вывод должен быть пустым.
DATABASE_URL="$CLONE_URL" npx prisma migrate diff \
  --from-schema-datasource prisma/schema.prisma \
  --to-schema-datamodel prisma/schema.prisma --script
```

После этого на клоне: пересчитать число строк в `User`, `RadarEvent`,
`Order`, `Trade`, `Position` и сравнить с боевой базой; открыть API
против клона и пройти маршруты радара, кошельков и портфеля.

Только пройдя этот шаг целиком, идти дальше.

## Шаг 2. Боевая база

Ни одна команда этого раздела не выполнена.

1. Убедиться, что не идёт развёртывание на Render и не работают
   воркеры, пишущие в базу.
2. Сделать полный backup и **проверить восстановление**: backup,
   который не разворачивали, — это надежда, а не резервная копия.
3. Открыть окно обслуживания. Записи в момент `migrate deploy`
   допустимы — новые таблицы никого не блокируют, — но окно нужно
   на случай отката.
4. Повторить сверку из шага 0 против боевой базы. Между проверкой
   и применением могло пройти время.
5. Сверить контрольную сумму файла baseline с той, что проверяли
   на клоне:
   ```bash
   shasum -a 256 prisma/migrations/0_baseline/migration.sql
   ```
6. Пометить baseline выполненным:
   ```bash
   DATABASE_URL="$(cat ~/.memex-prod-url)" \
     npx prisma migrate resolve --applied 0_baseline
   ```
   Команда только вписывает строку в `_prisma_migrations`.
   SQL baseline на существующей схеме не исполняется — таблицы
   в ней уже есть.
7. Проверить запись:
   ```bash
   DATABASE_URL="$(cat ~/.memex-prod-url)" npx prisma migrate status
   ```
   Ожидается: `0_baseline` применён, feature-миграция — нет.
8. Применить feature-миграцию отдельной командой:
   ```bash
   DATABASE_URL="$(cat ~/.memex-prod-url)" npx prisma migrate deploy
   ```
9. Проверить результат: `migrate status` без незавершённых миграций,
   `migrate diff` от базы к схеме без разницы, две новые таблицы
   и пять новых колонок в `User` на месте, счётчики строк в старых
   таблицах не изменились.

## Шаг 3. После применения

Отдельного заполнения данных не требуется: обе новые таблицы
начинают пустыми и наполняются по мере работы.

Проверить после применения:

```bash
DATABASE_URL="..." npx prisma migrate status
```

Ожидается: обе миграции применены, незавершённых нет.

**Пробный период сразу доступен.** Он выдаётся по нажатию, а не
автоматически, и требует подтверждённого адреса почты.

Проверьте до открытия доступа, что настроена доставка писем:
`EMAIL_PROVIDER=resend`, `EMAIL_FROM` на подтверждённом домене
и `RESEND_API_KEY`. Приложение не стартует, если провайдер выбран,
а ключа или отправителя нет; при `EMAIL_PROVIDER=disabled` оно
стартует, но запрос кода честно отвечает `EMAIL_DELIVERY_UNAVAILABLE`,
и пробный период получить нельзя. Подробности — в `docs/email.md`.

## Откат

Feature-миграция добавляет две таблицы, три перечисления и пять
колонок в `User`. Существующих данных она не меняет, поэтому откат
безопасен — с одной оговоркой: удаление колонок `User` уничтожает
записи о подтверждении почты, и подтверждать адреса придётся заново.

```sql
DROP TABLE IF EXISTS "EntitlementAudit";
DROP TABLE IF EXISTS "Subscription";
DROP TYPE IF EXISTS "SubscriptionSource";
DROP TYPE IF EXISTS "SubscriptionStatus";
DROP TYPE IF EXISTS "PlanCode";
ALTER TABLE "User"
  DROP COLUMN IF EXISTS "emailVerifiedAt",
  DROP COLUMN IF EXISTS "emailCodeHash",
  DROP COLUMN IF EXISTS "emailCodeIssuedAt",
  DROP COLUMN IF EXISTS "emailCodeExpires",
  DROP COLUMN IF EXISTS "emailCodeAttempts";
DELETE FROM "_prisma_migrations"
  WHERE "migration_name" = '20260821120000_add_subscriptions_and_trial';
```

Отката baseline не существует и не должно: он ничего не выполнял.
Если помечать его пришлось ошибочно, строка удаляется из
`_prisma_migrations` вручную, и это всё.

Предпочтительный способ исправления — не откат, а следующая миграция.
Откат имеет смысл только пока новыми таблицами никто не пользуется.
Как только появятся оплаченные подписки, `DROP TABLE "Subscription"`
уничтожит единственную запись о том, кто и за что заплатил.

## Чего в этом заходе делать нельзя

- Выполнять `migrate resolve`, `migrate deploy` или `db push`
  на боевой базе.
- Менять боевую схему.
- Редактировать `0_baseline/migration.sql` после того, как его
  пометили выполненным хотя бы в одной среде: контрольная сумма
  перестанет сходиться, и Prisma сообщит об этом на следующем
  развёртывании.
- Включать `FUNDING_ENABLED` до решения по подписи транзакций
  (см. `docs/custody.md`).
