# Архитектура

## Принятые решения и их цена

### Кастодиальная модель

Платформа хранит приватные ключи пользователей. Это даёт UX уровня Binance
(вход по email, мгновенные сделки, копитрейдинг без подтверждений в кошельке),
но переносит на вас три обязательства:

1. **Безопасность ключей.** Реализовано конвертное шифрование:
   ключ → AES-256-GCM(DEK) → DEK → KMS. Дамп базы без доступа к KMS бесполезен.
   `KMS_PROVIDER=local` жёстко запрещён в production на уровне кода.
2. **Платёжеспособность.** Обязательство перед пользователем возникает в момент
   зачисления депозита. Резервы должны быть 1:1, а расхождения — видны.
   Для этого баланс ведётся двойной записью: `LedgerEntry` — источник истины,
   `Balance` — производный агрегат, сверка через `/admin/reconcile/:userId`.
3. **Регуляторный статус.** См. `LEGAL-RISK.md`.

Альтернатива, от которой отказались: embedded wallet (Privy/Turnkey). Она даёт
80% того же UX без хранения ключей и без большей части лицензионных требований.
Если сроки или юрисдикция окажутся проблемой — переход туда потребует замены
только слоя `Wallet` и `crypto.ts`, остальная система не изменится.

### Исполнение через агрегаторы, а не свой AMM

Jupiter на Solana и 0x на EVM дают маршрутизацию по десяткам пулов. Свой роутер
означал бы худшее исполнение при кратно большей стоимости разработки. Свои
контракты имеют смысл только когда нужно собирать комиссию on-chain или
батчить копитрейд-сделки в одну транзакцию — это следующий этап, не первый.

### Средневзвешенная стоимость (WAC) вместо FIFO

Мем-коины набираются десятками мелких докупок. FIFO породил бы взрывной рост
числа лотов и неочевидные для пользователя расчёты при частичных выходах.
WAC даёт одну цифру `avgCost` на позицию, которую можно показать в интерфейсе
и воспроизвести при споре. Ключевое свойство: `avgCost` не меняется при продаже.

### Учёт копируемой доли позиции

Позиция может быть набрана частично вручную, частично копированием. Поле
`Position.copiedQuantity` отслеживает вторую часть, и при продаже комиссия
берётся пропорционально: если 40% позиции пришло из копитрейдинга, комиссией
облагается 40% прибыли. Без этого пользователь платил бы за собственные решения.

## Поток рыночного ордера

```
POST /orders
  ↓ проверка идемпотентности (Idempotency-Key)
  ↓ создание Order (PENDING)
executeOrder()
  ↓ 1. котировка у агрегатора
  ↓ 2. validateQuote — проскальзывание и price impact  ← отказ ДО списания денег
  ↓ 3. подпись ключом из KMS (ключ живёт только внутри withPrivateKey)
  ↓ 4. отправка в сеть, ожидание подтверждения
  ↓ 5. SERIALIZABLE-транзакция:
        debit(tokenIn) → applyBuy/applySell → calcPerformanceFee
        → credit(tokenOut - fee) → FeeLedger → Trade → Order.status
```

Порядок «сначала сеть, потом БД» выбран сознательно. Обратный порядок
(списать → отправить) при упавшей транзакции оставляет пользователя без денег
и без токенов, и восстановление требует ручного разбора.

## Поток копитрейдинга

```
Лидер: POST /orders (MARKET) → executeOrder → FILLED
  ↓ (асинхронно, не блокирует ответ лидеру)
fanoutLeaderTrade()
  ↓ для каждого подписчика: decideCopy(cfg, state, trade)
  ↓   проверки: заморозка → KYC → сеть → ликвидность → риск-скор
  ↓            → дневной лимит убытка → лимит позиций → размер
  ↓ создание Order(source=COPY_TRADE, parentOrderId=<лидер>)
copy-executor воркер: пачками по 10, executeOrder на каждую
```

Лидер исполняется первым — иначе платформу справедливо обвинят во фронтране
собственных клиентов. Отказ по одному подписчику не влияет на остальных
и всегда логируется с человекочитаемой причиной.

## Комиссия 10%: точная механика

Удерживается **при выходе**, из выручки, в валюте котировки:

```
прибыль = выручка − (средняя цена входа × проданное количество) − комиссии сети
если прибыль > 0:
    база = прибыль × доля_копитрейда
    комиссия = база × 10%
    лидеру 70%, платформе 30%
иначе:
    комиссия = 0
```

Каждое удержание пишется в `FeeLedger` вместе с `calcSnapshot` — снимком
входных данных расчёта. Через полгода это единственный способ ответить
на вопрос «откуда взялись эти $47».

**Известный конфликтный сценарий.** В выбранной модели пользователь платит
комиссию с прибыльной сделки, даже если суммарно он в минусе: потерял $500
на одной позиции, заработал $200 на другой — заплатит $20. Это законно
и распространено, но вызывает претензии. В `calcPerformanceFee` уже реализован
режим `useLossCarryForward`, который переносит убытки и гасит ими будущую
прибыль. Включается одним флагом. Рекомендую включить до запуска.

## Устойчивость

| Риск | Что сделано |
|---|---|
| Двойное списание при повторном запросе | `Idempotency-Key` на создании ордера |
| Гонка балансов при параллельных сделках | SERIALIZABLE + ретраи, `Balance.version` |
| Два воркера исполняют один ордер | атомарный захват через `updateMany` по статусу |
| Расхождение баланса и журнала | двойная запись + `reconcileUser` |
| Исполнение по мусорной цене | `validateQuote` до отправки, лимит price impact |
| Токен-ханипот в колле | `assessToken` блокирует публикацию при score ≥ 85 |
| Каскад копирования (копия копии) | `fanoutLeaderTrade` отклоняет `source=COPY_TRADE` |
| Заморозка аккаунта не отменяет лимитки | админ-хендлер отменяет открытые ордера |
| Утечка ключей через логи | `pino.redact` на всех чувствительных путях |
