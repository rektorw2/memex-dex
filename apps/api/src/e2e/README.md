# Сквозной стенд PAPER-режима и подготовки LIVE

Сценарии проходят полный путь на настоящей базе:

```
управляемый сигнал → очередь → воркер → решение → распределение капитала
→ PAPER-счёт и журнал → позиция и PnL → снимок /paper-agent
```

Ни воркер, ни служба капитала, ни HTTP-маршрут не подменены. Настоящие
и схема, и миграции, и клиент Prisma.

## Что подменено и почему

| Подменено | Причина |
| --- | --- |
| Часы (`vi.setSystemTime`) | Иначе сценарий «решение опоздало» пришлось бы ждать по-настоящему. |
| Внешний поставщик данных | Заменён управляемым источником `services/paper-test-source.ts` — тем самым, что в production выключен. |
| Сеть (`fetch`) | Запрещена целиком. Это не удобство, а проверка: PAPER-режим не имеет права никуда ходить. |

Больше ничего. В частности, `lib/prisma.ts` не мокается: стенд лишь
подставляет `DATABASE_URL` до создания клиента, и дальше работает тот же
код, что в production.

## Что внутри

| Файл | О чём |
| --- | --- |
| `paper-scenarios.e2e.test.ts` | Одиннадцать сценариев PAPER: прибыль, убыток, нет цены, скачок цены, дубликат, перезапуск, экспозиция, число позиций, дневной лимит, просадка, kill switch. |
| `idempotency.e2e.test.ts` | Точки прерывания: повторная доставка, обрыв между резервом и позицией, обрыв после закрытия, гонка четырёх проходов. |
| `schema-migration.e2e.test.ts` | Схема накатана целиком, включая многокомандные миграции. |
| `schema-transition.e2e.test.ts` | Переход базы, отставшей на четыре миграции Phase 4, настоящим `migrate deploy`. У каждого теста своя временная база `memex_e2e_transition_<...>`, которую он сам создаёт и удаляет. |
| `live-devnet.e2e.test.ts` | Готовность LIVE devnet без внешних секретов. Недостижимое помечено `BLOCKED_EXTERNAL` и не выдаётся за проверенное. |

## Запуск

Нужна **пустая** база PostgreSQL. Стенд очищает данные между сценариями,
поэтому имя базы обязано содержать `test` или `e2e` — иначе он откажется
стартовать.

```bash
createdb memex_e2e

E2E_DATABASE_URL=postgresql://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@localhost:5432/memex_e2e \
  npm run test:e2e
```

Схема накатывается автоматически при первом запуске: применяются те же
файлы из `prisma/migrations` и заполняется та же таблица истории, что
пишет `prisma migrate deploy`.

## Что проверяет каждый сценарий

Для каждого из одиннадцати:

- итоговое состояние `PaperAgentRun`;
- код решения;
- изменение или неизменность баланса PAPER-счёта;
- резерв и экспозиция;
- число открытых позиций;
- записи в `PaperAgentCapitalLedger`;
- ответ `/paper-agent`;
- **после каждого**: ни одного намерения транзакции, ни одной попытки
  подписи, ни одного вывода, ни одного исходящего запроса;
- повторный проход не создаёт дублей.

## Сборка ядра

API импортирует `@memex/core` как **собранный** пакет — из
`packages/core/dist`, а не из `src`. Пока сборка не обновлена, тесты
API проверяют прошлую версию правил ядра.

Это уже случалось: правка бухгалтерии в `src` дала 74/75, а после
`npm run build -w @memex/core` тот же прогон дал 75/75. Опасность не в
потерянном времени, а в том, что устаревшая сборка одинаково легко
даёт и ложное падение, и ложный успех — а зелёный прогон на коде,
которого больше нет, выглядит доказательством.

Поэтому защита двойная:

1. `npm run test:e2e` пересобирает ядро сам — через `pretest:e2e`
   в `apps/api/package.json`. Работают оба способа запуска:

   ```bash
   npm run test:e2e
   npm run test:e2e -w @memex/api
   ```

   Сборка вызывается относительным путём (`tsc -p ../../packages/core/tsconfig.json`),
   поэтому не зависит от того, из какого каталога запущена команда.

2. `global-setup.ts` проверяет свежесть до всего остального и
   останавливает прогон, если `dist` старше `src`. Это на случай
   запуска `vitest` напрямую, минуя npm-скрипт. Тот же контракт
   проверяется в обычном наборе — `src/lib/core-build-freshness.test.ts`,
   — чтобы `npm test` тоже не проходил на устаревшей сборке.

Проверка сравнивает время изменения файлов и честно не притворяется
большим: она не доказывает, что сборка правильная, только что она
не старше исходников.

## Безопасность

Конфигурация стенда (`vitest.e2e.config.ts`) держит контур закрытым:
`EXECUTION_MODE=paper`, mainnet, выводы, LIVE-исполнение и подпись
выключены. Единственная включённая настройка — `PAPER_TEST_SOURCE_ENABLED`,
и она допустима только в этом сочетании: запуск с боевым режимом или
mainnet останавливается проверкой в `lib/env.ts`.

Стенд не входит в `npm test` намеренно. Тест, который без базы молча
превращается в «пропущено», — это зелёный результат, ничего не значащий.
